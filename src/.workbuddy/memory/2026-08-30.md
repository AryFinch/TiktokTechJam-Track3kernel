# 2026-08-30 — Tech Jam: 5 transformer optimization variants

## What I did
Benchmarked 5 different optimized versions of `torch_transformer_benchmark.py`,
each in its own file under `solutions/`. The harness (accuracy + timing) is
unchanged across copies, so all numbers are directly comparable.

| Variant | Idea                                | Default-config speedup |
| ------- | ----------------------------------- | ---------------------: |
| V0      | No change (sanity)                  | 1.00×                  |
| V1      | `F.scaled_dot_product_attention`    | **8.47×**              |
| V2      | `torch.compile` (default)           | 0.35×  (slower)        |
| V3      | QKV fusion + GELU-tanh              | 1.01×                  |
| V4      | SDPA + `torch.compile`              | 0.36×  (slower)        |

## Environment
- Mac M4 Pro, macOS 15.7.9, arm64.
- Python 3.13.12 in `/Users/ary/.workbuddy/binaries/python/envs/torchjam`.
- PyTorch 2.13.0 with MPS, no CUDA. `--device mps` everywhere.
- Default config: batch=8, seq=128, d_model=512, heads=8, ffn=2048, layers=6, fp32, no causal, no padding.

## Headline findings
- **SDPA is the single biggest lever.** At default config 8.5×; at seq=256 it
  climbs to 15×; at seq=512 it hits 20.2×. The win scales with the attention
  matrix size, exactly as the theory predicts (O(S²) → O(S·D) memory).
- **torch.compile is currently a net loss on MPS.** V2 and V4 are both ~3× slower
  than baseline. The Inductor → Metal codegen is less mature than CUDA, and the
  per-op wrapper overhead exceeds the fusion savings for this model size.
- **Hand-rolled micro-fusions don't help when the workload is GEMM-bound.** V3
  (QKV + GELU-tanh) gives 1.01× because the baseline is dominated by 6 large
  `Linear(512, 2048)` matmuls — rearranging GEMM borders or replacing tiny
  elementwise kernels doesn't change the dominant cost.
- **Optimizations don't stack additively.** V4 = V1 + V2 should logically be
  ≥ V1 but is 0.36× because Inductor's wrapper overhead eats the SDPA win.

## Key gotcha to remember
On the MPS backend, `F.scaled_dot_product_attention` **rejects
`is_causal=True` together with `attn_mask`** with the error
"Explicit attn_mask should not be set when is_causal=True". When both masks
are needed (causal + padding), fuse them into a single additive attn_mask.
